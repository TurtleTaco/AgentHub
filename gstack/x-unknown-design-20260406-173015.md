# Design: Distributed OpenSpec — Task Coordination for Dev Collectives

## Problem Statement

OpenSpec provides a structured spec-driven development pipeline (proposal -> specs -> design -> tasks -> implement) that runs locally. There's no mechanism for distributing this pipeline across multiple contributors on the internet. Dev collectives — groups of developers who want to collaborate without centralized coordination — currently have no way to:

1. Distribute spec/design work across contributors with review gates
2. Parallelize implementation tasks across multiple AI agent nodes
3. Coordinate approvals and test verification across independent machines

The goal is to build a coordination layer on top of OpenSpec that lets contributors run nodes, discover available work, execute tasks (via AI agents), and submit results for community review.

## What Makes This Cool

This is a new category. No existing tool combines:
- Structured spec-driven workflow (OpenSpec's artifact DAG)
- Distributed autonomous execution (AI agents on contributor nodes)
- Community governance (consensus-based spec approval, reputation systems)

The endgame is an autonomous mesh where contributor nodes self-coordinate. Humans guide the spec/design phases. AI agents grind through implementation. "Continuously collapsing wave function" rather than waterfall with gates. (Self-evolving specs and AI-first review are aspirational, out of scope for all planned versions.)

## Constraints

- Git remains the source of truth for all artifacts (specs, designs, tasks, code)
- Contributors bring their own compute and AI API keys
- Spec/design phases are human-in-the-loop; implementation is autonomous
- Community consensus required for spec approval (not single maintainer)
- Centralized test runner acceptable for v1
- Must work as an OpenSpec extension (not a fork)
- No economic layer in v1 (no tokens, bounties, or payments)

## Premises

1. Git is the right foundation — artifacts live in repos, branches coordinate, PRs review
2. Human-in-the-loop for spec/design, autonomous AI agents for implementation
3. Community consensus for spec approval (threshold voting, see Governance section below)
4. Centralized test runner for v1 (trusted node runs test suite)
5. Task server coordinates; contributors bring their own compute

## Approaches Considered

### Approach A: Git + Task Server
Lightweight HTTP task server (FastAPI/SQLite or Go) with 4-5 endpoints. Git repos as artifact storage. Contributor nodes poll for tasks, run AI agents locally, push results as branches.
- Effort: S (weekend)
- Demoable fast, simple, but central server is a coordination bottleneck

### Approach B: OpenSpec Native Extension
Build coordination as an OpenSpec schema extension. Task server reads tasks.md and exposes work items. Uses OpenSpec's existing artifact DAG and CLI.
- Effort: M (1-2 weeks)
- Deeply integrated, contributors using OpenSpec get distribution natively

## Recommended Approach

**A + B hybrid**: Build the task server (Approach A) as an OpenSpec native extension (Approach B).

The task server is a lightweight HTTP service that understands OpenSpec's artifact structure natively. It reads `tasks.md` files, exposes them as claimable work items, and tracks state. But it also understands the full artifact DAG — so it can register "generate design" tasks when specs are approved, not just implementation tasks.

### Authentication (v1)

Contributors authenticate via GitHub OAuth tokens. The task server validates tokens against the project's GitHub org/repo. Each API request includes a Bearer token. Authorization rules:

- **Any authenticated contributor** can: list tasks, claim tasks, submit results, view context
- **Registered reviewers** (project-configured) can: approve, reject
- **Project admins** can: register changes, trigger test runs, configure governance

Identity is tied to GitHub username. This is a v1 simplification; v2+ may use SSH keys or decentralized identity.

### Task Server Data Model

```
Project
  ├── id: string (repo slug)
  ├── repo_url: string (git remote)
  ├── governance: { approval_threshold: int (default 2) }
  └── contributors: [{ github_username, role: admin|reviewer|contributor }]

Change
  ├── id: string (OpenSpec change name)
  ├── project_id: string
  ├── phase: proposal|specs|design|tasks|implementation|testing|done
  └── branch: string (git branch ref)

Task
  ├── id: string (uuid)
  ├── change_id: string
  ├── type: spec_review|design|task_generation|implement|fix
  ├── state: available → claimed → submitted → approved|rejected
  ├── description: string
  ├── claimed_by: string|null (github username)
  ├── claimed_at: timestamp|null
  ├── lease_ttl: int (seconds, default 1800 = 30 min, renewable)
  ├── result_branch: string|null (git ref)
  ├── result_sha: string|null
  └── approvals: [{ by: string, at: timestamp }]

TestRun
  ├── id: string
  ├── change_id: string
  ├── branches: [string] (submitted branches to merge)
  ├── status: pending|running|passed|failed
  ├── command: string (e.g., "npm test")
  └── output: string|null (test output on failure)
```

### Task State Machine

```
  available ──claim──► claimed ──submit──► submitted ──approve──► approved
      ▲                   │                    │                     │
      │              lease expires         rejected              merged
      │                   │                    │
      └───────────────────┘                    │
      └────────────────────────────────────────┘
                    (back to available)
```

Lease renewal: `POST /tasks/{id}/renew` extends the lease by another 30 minutes from the time of renewal (sliding window). Max 3 renewals, for a maximum total lease duration of 2 hours from the original claim. After expiry, task returns to `available`.

**Concurrent claims**: `/claim` uses atomic compare-and-swap on task state (SQLite transaction). If the task is already claimed, returns `409 Conflict`. Nodes should retry with a different available task.

**Server failure recovery**: Leases expire naturally. On server restart, all expired leases are cleaned up and tasks return to `available`. Nodes should retry server requests with exponential backoff (1s, 2s, 4s, max 30s).

### Task Server API

```
POST   /projects/{id}/changes          Register a new change from OpenSpec
POST   /projects/{id}/tasks            Register tasks (from tasks.md parse)
GET    /projects/{id}/tasks             List tasks (filterable by state)
POST   /tasks/{id}/claim               Claim a task (returns lease with TTL)
POST   /tasks/{id}/submit              Submit result (git branch ref + commit SHA)
POST   /tasks/{id}/release             Release a claimed task (timeout or abandon)
POST   /tasks/{id}/renew               Renew lease (max 3 renewals)
POST   /tasks/{id}/approve             Community approval of submitted result
POST   /tasks/{id}/reject              Reject with feedback
GET    /tasks/{id}/context             Get context bundle (spec + design + relevant files)
POST   /projects/{id}/test-run         Trigger test run against submitted branches
GET    /projects/{id}/status            Pipeline status (what phase, what's pending)
```

### Notification Transport (v1)

Polling. Contributor nodes poll `GET /projects/{id}/tasks` every 30 seconds. The endpoint supports `If-None-Match` (ETag) for efficient polling. v2 adds WebSocket subscriptions for real-time push.

### Contributor Node

A CLI tool (or daemon) that:
1. Registers with the task server
2. Polls for available tasks matching its capabilities
3. Claims a task, gets a lease
4. Pulls the context branch from git
5. Assembles context: spec files, design files, relevant codebase files, test expectations
6. Invokes AI agent (using contributor's own API keys) with structured prompt
7. Writes output to a feature branch
8. Pushes branch, submits SHA to task server
9. Optionally monitors for review feedback

```
openspec-node start \
  --server https://coord.example.com \
  --repo git@github.com:collective/project.git \
  --capabilities "implement,design" \
  --model claude-sonnet-4-6
```

**Capability taxonomy (v1)**:
- `spec_review` — can review and amend specs (human-driven)
- `design` — can generate design.md from approved specs
- `task_generation` — can break design into tasks.md
- `implement` — can implement coding tasks (AI agent)
- `fix` — can fix failing tests (AI agent)
- `review` — can review submitted code (human or AI)

The task server matches available tasks to node capabilities. A node with `capabilities: "implement,fix"` will only see implementation and fix tasks.

### Context Assembly

Context assembly is the highest-risk area. The v1 approach below is a pragmatic starting point that will need iteration. A contributor node needs enough context to do useful work:

1. **Spec context**: The approved spec.md for this change
2. **Design context**: The approved design.md (for implementation tasks)
3. **Task context**: The specific task description from tasks.md
4. **Codebase context**: Relevant existing files the task touches
5. **Test context**: Expected test behavior, existing test patterns

**v1 approach**: The task server's `/context` endpoint returns a bundle:
```json
{
  "task": { "id": "...", "description": "..." },
  "spec": "contents of spec.md",
  "design": "contents of design.md",
  "relevant_files": ["src/auth.ts", "src/auth.test.ts"],
  "test_patterns": "contents of existing test file",
  "instructions": "generated prompt for AI agent"
}
```

File relevance is determined by (in order):
1. Files explicitly mentioned in design.md (regex extraction of file paths: patterns like `src/...`, `lib/...`, any path with a file extension)
2. Files matching keywords in the task description (grep task keywords against file names and function names)
3. Files co-changed in git history with already-identified files (`git log --follow --name-only`)
4. Default limit: context bundle capped at 400KB (~100K tokens), configurable per project. If exceeded, files are prioritized by relevance score (explicit mention > keyword match > co-change history). Large files are truncated to their first 200 lines with a note. For codebases exceeding this limit, the node can request specific files via `GET /tasks/{id}/context?files=path1,path2`.

### Community Governance (v1)

Simple threshold voting:
- Spec approval: requires N approvals from registered contributors
- Design approval: same
- Code review: at least 1 approval from a contributor who didn't write it
- N is configurable per project (default: 2)

**v2 vision (reputation system)**:
- Contributors earn trust through successful task completions
- Trusted contributors can auto-approve certain task types
- Review weight scales with reputation
- New contributors start with small, low-risk tasks

### Future Vision (out of scope for v1, directional only)

The task server is the v1 concession. Future evolution may include:
- **Federation**: Multiple task servers syncing state
- **P2P**: Nodes discover each other via DHT or gossip, no central server
- **Reputation**: Contributors earn trust through successful completions
- **AI-first review**: Agents reviewing each other's work

v1 must NOT be designed to accommodate these. They are aspirational directions. The API should be clean and simple, not over-abstracted for hypothetical future backends.

### Merge Strategy (v1)

Sequential merge in task dependency order. The test runner:
1. Creates a merge branch from the change's base branch
2. Merges submitted task branches one at a time, in the order tasks are numbered in tasks.md
3. If a merge conflict occurs: the conflicting task is rejected with context (original task branch, merge branch up to conflict point, conflict diff). A "fix" task is registered with the merge branch as the new base. The fix task creates a new branch from the merge branch.
4. Runs the test command after each branch is merged (sequential merge-and-test). The first merge that causes test failure identifies the guilty task.
5. If all tests pass after all merges: the merge branch becomes a PR against the base branch
6. If tests fail: the guilty task is rejected with test output attached, re-registered as a "fix" task

Maximum 3 retry cycles per change. After 3 cycles, the change is flagged for human intervention.

### Test Runner (v1)

The test runner is a single configurable command string stored in the project config:
```json
{ "test_command": "npm test", "test_timeout_seconds": 600 }
```

The test runner node must have the project's runtime dependencies installed. v1 assumes the project maintainer runs the test runner node. The test runner environment is NOT provisioned automatically... the operator is responsible for having the right Node/Python/Go/etc. version.

## Open Questions

1. **Task granularity**: How fine-grained should tasks be? One function per task? One file? One feature? This affects parallelism and merge complexity. (Recommendation: one task per numbered item in tasks.md, which typically corresponds to one logical unit of work.)
2. **Spec drift**: If implementation reveals the spec was wrong, how does a contributor node signal "this spec needs amendment" back to the community?
3. **AI model differences**: Different contributors may use different AI models (Claude, GPT, Gemini, local models). How do we handle quality variance? (v1: we don't. Tests are the quality gate.)
4. **OpenSpec plugin interface**: How exactly does the coordination server hook into OpenSpec's CLI? Does OpenSpec need changes to support this, or can it be a standalone tool that reads OpenSpec's file structure?

## Success Criteria

- Two contributor nodes on different machines can independently implement tasks from the same change
- The central test runner can merge results and verify correctness
- A contributor can claim a "generate design" task, run it, and submit for community review
- The full pipeline (proposal -> specs -> design -> tasks -> implement -> test -> merge) works end-to-end across at least 2 contributors
- Task claim/release semantics prevent duplicate work

- Task server distributed as a Docker image and/or single binary
- Docs integrated into OpenSpec's existing documentation site

## Reviewer Concerns

Remaining issues from adversarial review (2 rounds, 6/10 -> 7/10):

1. **`review` capability has no corresponding task type** — Review is handled via approval endpoints, not the task claim flow. This should be documented explicitly but is not a blocking issue.
2. **Code review vs spec review threshold rationale** — Spec/design approval requires N approvals; code review requires 1. The rationale (tests are the primary quality gate for code) should be stated explicitly.
3. **Context assembly indexing lifecycle** — When does the server clone/pull the repo to run relevance heuristics? At request time (lazy) or via background indexing? v1 recommendation: lazy (clone on first request, pull on subsequent).
4. **OpenSpec plugin interface** — Whether this is an extension or standalone tool is unresolved. v1 recommendation: standalone tool that reads OpenSpec's file structure, with integration as a v2 goal.

## What I noticed about how you think

- You immediately split the pipeline into human-judgment phases and machine-execution phases. That's a design instinct that avoids the trap of trying to automate everything at once.
- You chose "dev collectives" over solo builders or OSS maintainers. That tells me you're thinking about this as infrastructure for a new way of organizing, not just a productivity tool for existing workflows.
- You picked reputation + AI review + self-evolving specs but explicitly excluded economics. You're building for trust and intelligence, not incentives. That's a fundamentally different system than most "distributed work" platforms.
- You said "nothing close" exists. That's either blind spot or genuine insight. Given the specificity of the combination (structured spec DAG + distributed autonomous execution + community governance), I think it's genuine.
